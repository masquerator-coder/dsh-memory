### 最关键的几个实证结论（后续改动前务必回看）
- **smoke.mjs 有 ~17% 失败率**（12 次跑失败 2 次）。根因是 `store.ts:213/486` 的
  `ORDER BY updated DESC` / `ORDER BY ts DESC` 缺 tie-breaker，同毫秒写入的行顺序未定义。
  修法：`ORDER BY updated DESC, rowid DESC`。这条不修，其余任何结论都不可信。
- **真删路径在生产参数下不可达**：`heat.ts:112` 多加了一道 `quality < 60` 门槛（DESIGN 稿没有），
  而 `qualityScore` 对任何 ≥15 字的正常内容给 100 分。实测归档后过观察期 `deletedMem=0`。
  → v3 立项动机"库只增不减"实际没修上。
- **`overflowed` 分支不可达**：`demoteToBudget` 的可降级集合恰好等于 `usage().memory` 的统计集合，
  全降级后用量必为 0。导致 tools.ts 的"预算已满"提示、L1 逐条重试全是死代码。
- **`budgetUser` / `budgetTier0` 从未强制**（`budgetOver()` 只查 `usage().memory`），
  且 user 层设计为永生不可降级 → 注入区体积无上界。
- **`replace` 有两个数据损坏缺陷**：① 不更新 id，破坏"id = contentId(content)"不变式，
  去重失效产生完全重复条目；② 无 id 时的模糊匹配 `content.includes(e.content)` 方向反了，
  实测 content="用" 把整条记忆静默覆写成"用"。
- **提示注入面完全开放**：`inject.ts` 把记忆正文原样拼进 system prompt，无定界/转义/长度上限。
- **性能**：单次 add 随库容量线性劣化（4000 条时 52.8ms），recall 全表扫描（3000 条 17ms），
  `hasPendingCorrection` 在遗忘循环内逐条全表扫（O(归档×留痕)）。
- **`l0TimeoutMs` 是死配置**：`runL0` 接受 timeoutMs 但从不使用，L0 LLM 调用无超时
  （对比 refine.ts 的 llmText 是有 AbortController 的）。

### 项目约定/环境要点
- 编译必须用 monorepo 的 tsc：`node "D:/Apps/deepseek-harness/node_modules/typescript/bin/tsc" -p tsconfig.json`
  （tsconfig 里 typeRoots 和 6 条 paths 全写死 `D:/Apps/deepseek-harness/...` 绝对路径，换机器即失效）。
- `lib/` 是编译产物但已提交，消费者（git 安装）不带工具链；改 src 后必须重新编译并一起提交，
  否则 smoke.mjs（它 import 的是 `./lib/`）测的是旧代码。
- Node 22 下 `node:sqlite` 仍输出 ExperimentalWarning，package.json 缺 `engines` 声明。
